# 协作业务与状态机

本文描述现行业务，源码候选与已发布版本见 [README](../README.md)。AgileNest 面向课程、研究、竞赛与软件项目，报告、设计文件和代码均可作为成果，GitHub 只是可选证据链接。实验室采用团队内的 lab 类型项目，不另建实验数据或设备模型。接口见 [TEAM](TEAM.md)，实际验收见 [UX](UX.md)，未来能力只在 [ROADMAP](ROADMAP.md) 维护。

## 完整工作链路

| 阶段 | 操作 | 保留的结果 |
|---|---|---|
| 团队与项目 | 完善团队资料/公告、成员职务、项目目录 | 团队归属与当前权限 |
| 目标与资料 | 分类内建立主题，创建文档或上传原件 | 原文件、正文版本、协作者与评论 |
| 发布与分工 | 写明目标、验收要求，姓名指派或等待认领 | 负责人、日期、标签、依赖与来源版本 |
| 执行与沟通 | 任务讨论、回复、附件、提及和工时 | 执行记录及讨论处理历史 |
| 成果提交 | 完成说明、验证结果、文件/链接和逐项自检 | 不可变提交 v1/v2 |
| 指定版本验收 | 逐项核对，明确问题位置及通过条件 | 评审结论、打回意见与重交历史 |
| 阶段交付 | 绑定通过版本，处理问题并核对清单 | 交付快照、归档与导出 |

资料库存放原件，讨论附件用于交流，正式提交单独选择并绑定本次证据。讨论解决不等于任务验收；关注、提醒和分享链接不增加访问权限。

## 数据与导航链路

```mermaid

  T[团队空间] --> M
  T --> P[课程 / 实验室 / 竞赛项目]
  P --> K[任务与子任务]
  K --> W[工时]
  K --> E[状态事件]
  P --> N[里程碑]
  P --> F[主题目录与资料版本]
  K --> S[不可变成果提交 v1 / v2]
  S --> R[逐项验收]
  R --> D[已通过版本的阶段交付]
```

项目访问权限继承团队成员关系；用户在不同团队内的职务可以不同。邀请码加入默认组员，管理员独立授予可叠加职务，学术身份不授予权限。团队空间展示成员与 active 项目数量，项目卡片展示顶层任务状态分布，完成度为已验收顶层任务 / 顶层任务总数；无顶层任务时明确展示零项。

选中过项目后，侧栏在全局页面与操作刷新中继续展示该项目，直到进入或切换另一项目。最近选择按账号保存在浏览器，项目名称和入口仍来自当前可访问项目列表；首次不自动选择，失去访问权后不恢复失效导航。保留项目不代表把工作台、团队资料或私人日历变成该项目的数据。

工作台以“待办速览 → 任务分类 → 筛选与任务列表 → 项目入口”组织信息。今日到期、逾期、需修改及待我验收均来自本人有权限的活跃项目队列，可直接进入对应列表。搜索常驻，项目/日期/状态/排序集中在可展开区域，筛选标签支持逐项清除；网址保留条件与页码，每页显示 12 项，支持智能排序、截止日期及最近更新。摘要统计全部活跃项目，列表统计当前筛选结果，两者范围明确区分。

同账号的全局页面同步其他标签页的最近选择；正在查看项目的页面始终显示地址对应项目，避免两个标签互相切换。菜单明确选择当前项目也会更新最近选择。手机抽屉随页面路径切换关闭，桌面收起/展开保留键盘焦点。

## 五态唯一真相

```mermaid
stateDiagram-v2
  state "待认领" as unclaimed
  state "进行中" as in_progress
  state "待验收" as submitted
  state "待修改" as rejected
  state "已完成" as accepted
  unclaimed --> in_progress: claim / assign
  in_progress --> submitted: submit + delivery
  submitted --> accepted: accept + review
  submitted --> rejected: reject + review
  rejected --> submitted: resubmit + delivery
  in_progress --> unclaimed: unclaim
  rejected --> unclaimed: unclaim
  rejected --> in_progress: assign
  accepted --> in_progress: reopen
```

`assign` 也允许在进行中重新指派负责人。只有 `accepted` 是已完成；提交不直接完成。待修改是验收反馈分支，修改后回到待验收。状态代码与数据库 enum 保持兼容。

模块内部 `tasks/states.ts` 的 `TRANSITIONS` 是唯一合法边集合。`availableTransitions(task, role, actorId)` 使用任务权限快照与负责人判断；`ACTION_ROLES` 仅保留旧调用兼容。任务权限来自 `identity/client.capabilitiesFor` 按职务并集与项目场景计算。界面、看板与服务端复用公开规则，服务端重新核对当前权限。

## 动作与职务

学术身份不参与授权。管理员、副管理员、指导老师、队长、组员可叠加；完整能力矩阵见 [IDENTITY.md](IDENTITY.md)。指导老师负责验收，叠加组员后可以执行自己的任务；队长协调实验室/竞赛的指派和项目维护，验收仍由管理员、副管理员或指导老师执行。

负责人选择具有执行职务的真实团队成员。提交/重交必须验收清单、完成说明、验证结果、证据和逐项自检；验收绑定当前提交版本，打回要求未通过项的问题位置与通过条件；创建时指定负责人同样校验，普通组员不能通过创建接口指派别人。成员查询也在 service 中检查访问权限。职务调整锁定团队，禁止降级最后一位管理员。

发布任务至少一项非空、可核对的验收标准，与任务同事务保存，不新增第六个草稿状态。历史任务缺标准时明确提示先完善，不能伪造旧要求。任务处于 submitted/accepted 时冻结验收要求；打回或重开后可持版本调整，新提交使用新要求，原提交和评审快照保留。

每次 submit/resubmit 产生独立递增版本，保留当时说明、验证、链接/文件和自检。未达到项可在自检中如实记录；accept 必须核对当前提交快照且全部项通过，reject 记录具体修改要求。历史 v1/v2 选择仅改变阅读对象，不改变操作区的当前待验收版本；旧 submissionId 返回冲突，不能验收历史选择或覆盖新版。

任务最多两层，创建后不能更换父任务。待验收或已完成的父任务不能继续拆分；验收父任务前需全部子任务通过，重开已完成子任务前需先重开父任务。父任务行锁协调子任务写入与验收，避免并发更新产生相互矛盾的完成状态。项目完成率只统计顶层任务，子任务进度在详情独立展示。

## 写入与刷新

`transitionTask()` 是所有既有任务状态变更入口：先检查项目访问和能力，在事务内先锁团队并重查成员资格，再按需锁父任务与当前任务，读取最新状态并查表，最后同时写成果/评审、任务与活动事件。并发认领会让后一请求看到新的状态并返回 409；资源证据按固定顺序锁定并绑定引用。通知失败不撤销已提交的任务操作。

看板移动通过 `moveTask()` 调用任务公开契约；普通动作仍兼容 `note`，提交/重交传 `delivery`，通过/打回传 `review`，不能用文字绕过结构化校验。状态、负责人和普通属性分别提交，混合写入明确拒绝，避免静默丢弃字段。页面在服务端确认后更新；取消或失败仍留在原列。

Server Actions 刷新实际任务所属项目的页面，包含看板、表格、详情、验收台与工作台。任务详情同时校验 URL 中的 projectId 和任务真实归属。活动记录可追踪操作人、动作、说明，不宣称具有不可篡改存证能力。

## 多视图与实现边界

任务池、看板与表格共用 URL 筛选 `q/status/assigneeId/priority/milestoneId/labelId/blocked`，`groupBy` 控制分组；本人保存视图保留合法条件，分享链接不扩权。看板与表格 `task=UUID` 保留当前详情和筛选，关闭只移除详情参数，浏览器前进/后退可恢复。API 列顺序继续保持原有契约，页面将待修改放在已完成前；主路径图单独展示验收反馈分支。负责人/优先级/里程碑分组用于浏览，只有状态分组支持拖动。

路由只做组合壳；模块的 service、actions、ui、views 分别负责权限业务、边界写入、客户端交互和服务端组装。业务跨模块只用根契约，公开 UI 入口登记于 [TEAM.md](TEAM.md)，客户端纯函数不导入 DB/session。登录链路与依赖保持既有内容，身份、职务及个人资料表只追加；既有数据库使用文档中的可重复迁移升级。

视觉恢复品牌 `#294a78`、点缀 `#bf6a34`，状态统一用 StatusPill。弹窗使用已有 Radix，拖动复用已有 dnd-kit；提供按钮等价入口、焦点管理与减少动效。完整交互规则、参考来源与手动验收见 [UX.md](UX.md)。

## 分类主题、资料与回收

团队/项目空间内先选资料分类，再创建主题与子文件夹；目录最多八层，同空间同分类移动，校验循环和整个子树深度。当前路径新建/上传同步保存位置，文档版本、文件原件、引文评论与任务来源分别保留；收到深链接不增加读取或管理权限。

项目目录最多四层，只整理入口，不改变项目所属团队。资料支持位置/置顶、范围/分类/类型/关键词筛选，旧混合目录兼容。内容互链支持资料↔资料及同项目资料↔任务，读取目标与反链时重新检查权限。

当前团队成员可读共享资料；每份资料可授予 comment/edit，评论范围为 team/collaborators，edit 不授予管理权，尚未提供“仅选定成员可读”。引文评论保留行号、正文版本、单层回复、编辑/解决/撤回历史与提及快照。作者及资料管理者管理协作者，正文编辑使用版本检查。

原文件不可覆盖，正文保留修订历史；文件预览与下载经过服务端鉴权，单文件最多 10 MB。Marker 仅用于导入用户提供的 Markdown/JSON 转换产物；PDF/Office 没有真实转换正文时提供原件预览/下载，不宣称运行 OCR。个人 AI 文件与团队资料分开保存，详见 [AI](AI.md)。

资料回收使用版本检查，原件和历史仍保存，回收内容从普通列表、预览、下载和新增关联中隔离。成果、讨论和任务来源等引用保护先检查，不能用回收绕过证据保留。作者或有资料管理能力的成员恢复同一资料及原路径；已恢复或旧版本操作返回 409。目录只能空目录删除，未实现递归回收、永久清除或自动过期。

## 阶段交付与统一协作入口

delivery 组合任务公开的已通过版本，保存责任人、日期、检查项、评审问题与记录快照。绑定时检查任务所属项目、accepted 状态及真实通过的 submissionId；阶段确认再次核对绑定版本、清单和未解决问题。阶段状态与任务五态分开，归档/恢复不替代任务验收；Markdown/JSON 导出指定交付记录版本，不重写旧任务成果。

消息与 AI 草稿统一右下角协作入口。本人消息按真实未读、类别与来源呈现，短时气泡只是预览，消失不自动已读；关闭预览仍可在通知偏好恢复。确认/取消使用既有 Radix 原语，等待、错误、Esc 和焦点恢复要求见 [前端指南](FRONTEND-DESIGN-GUIDE.md)。站内通知不等于飞书投递或系统 Web Push；AI 仅本人本地草稿，Marker 仅导入真实转换产物，未运行 OCR/模型。

## 个人时间安排

个人日程与项目任务分别建模：`personal_schedules` 归本人，项目日历来自任务截止与里程碑。个人日程不触发认领、提交、验收或工时，不向他人发送安排；本人可显式启用日程提醒。添加和编辑不会隐式改变任务。查询限定账号和自然月，以用户/日期索引支撑；编辑和删除使用递增版本与用户条件原子写入，冲突返回 409。路由、页面和 API 复用 calendar 公开契约，边界详见 [SCHEDULES.md](SCHEDULES.md)。

## 任务组织与文档来源

依赖使用同项目有向无环关系，blockedBy/blocking两端可见。前置任务未验收时，availableTransitions隐藏提交/重交/通过，transitionTask事务内再核对；后续已提交或验收时保护前置重开。关系存在时删除不能绕过依赖，五态定义不变。

文档/会议行动项要求可读真实文档和当前来源版本，摘录必须在正文中；任务、创建事件和来源快照同事务提交，稳定requestKey防重复。源文档版本、标题、摘录与回链保留，来源引用保护删除。编辑文档不会改写已创建任务或既有提交版本。

内容协作使用版本409，讨论与正文评论的提及保存姓名快照，结构性解决/撤回保留旧快照。关注/通知事件记录同事务并幂等；个人日程提醒的收据按日程版本和提醒版本唯一。实时编辑和群聊协议是独立后续方案，不用普通全文覆盖实现。

## 关注、消息与本人视图

任务讨论支持单层回复、版本冲突、历史分页及旧通知定位。正文只有作者可编辑；处理权限由任务能力决定，附件与正式成果证据分别选择，草稿按账号隔离。

本人保存视图持久化项目、名称、布局、分组与合法筛选；改名、更新和删除校验版本。保存项私有，分享使用筛选 URL；失效标签保留原条件并提示，不扩大团队读取范围。

站内通知包括提及、参与及事项/项目关注，排除本人、离队和外部成员，事件幂等。取消事项关注覆盖项目继承；关闭通知类别不删除已有消息，也不回放旧事件。任务、讨论、提及、资料、提醒和气泡偏好归本人。日程提醒规则见 [SCHEDULES](SCHEDULES.md)，飞书投递边界见 [FEISHU](FEISHU.md)。
