## 已落实的产品主线

1. **组织与权限**：学术身份由本人维护、另一管理员按版本确认；管理员/指导老师/队长/队员可叠加。团队资料、公告、邀请码有效期和成员退出/移除已加入代码，最后管理员和未完成任务负责人受保护。
2. **任务执行**：任务池、看板、表格共享筛选；详情有目标、负责人、日期、子任务、工时、验收要求和真实活动。看板/表格用 `task` URL 打开详情；任务池保持独立详情入口。
3. **成果交付**：至少一项验收要求；完成说明、验证结果、链接或文件证据、逐项自检缺一不可。每次提交保存不可变快照，重交产生新版本，旧成果和意见保留。
4. **逐项验收**：老师/管理员选择当前提交版本，逐项核对；全部通过才能完成，打回需指出未通过项、问题位置和通过条件。旧页面不能覆盖新提交，子任务约束仍有效。
5. **资料中心**：团队共享及项目资料分层，文档、链接和原文件分别组织；分类/标签/搜索、Markdown 编辑与历史、CSV/JSON 展示、图片/PDF 预览、Office/ZIP 下载。提交引用的文件不能删除或覆盖。
6. **协作反馈**：工作台按职务显示执行/验收队列，通知直达任务；统计明确顶层验收比例与工时。个人日程和 AI 本地草稿保持本人范围。

## 下一轮优先顺序

- **P0 协作易用性**：根据实际试用反馈完善提交/验收字段提示、资料编辑、团队入口和错误恢复。只补真实操作，不堆无用 Dashboard 指标。
- **P1 浏览连续性**：项目日历支持的筛选与任务视图对齐；先冻结 q/priority/risk/date 的含义，明确不支持的条件。随后考虑资料目录/任务讨论等独立能力的数据与历史策略。
- **P2 研发集成**：先评估只读 PR 证据、仓库归属和权限，再决定 GitHub 同步；Sprint、历史分析、AI 执行继续单独立项。现有手工成果链接不等于自动同步或构建检查。
- **最终验收与发布**：用户给出最终要求后统一验收；修正完成再合入主分支并验证，正式 tag/ZIP 不从本轮候选推断。
